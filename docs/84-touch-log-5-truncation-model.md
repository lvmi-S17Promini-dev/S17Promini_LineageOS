# touch-log-5：读出内容与截断固件模型吻合

firmware_status为read-probe/done、pages197、result0；id_tail12、status00，CRC b1bd5c8f，原厂期望1655298b，差异22488字节，首32字节与原厂内嵌固件完全相同。退出复位后实时版本0000，IRQ报告仍0，没有触摸事件。

离线检验用已验证原厂50192字节固件，保留[0,0x6ac9)，其后全填FF。模型CRC恰好b1bd5c8f，差异字节数恰好22488，首32字节自然吻合。其余全部补0模型（同差异数的边界0x69af）CRC为d95bbf25，不匹配。计算记录extracted/metadata/touch-log-5-truncation-model.json。

这强烈支持当前读出内容类似“部分原厂内容+后段空白”，但尚未保存完整二进制读出。CRC32、差异总数和首32字节不能数学上唯一恢复全部内容，不应声称已逐字节证明实际存储在0x6ac9截断，也不能据此确定损坏发生时间。id_tail12仅为原厂9f读取方式的尾字节，不是完整厂商/型号识别；不能据它断言板上存储类型。

正常LineageOS+prebuilt内核触摸正常的用户基线仍成立。原厂自动固件处理、旧恢复环境被打断的升级、当前启动模式的影响都需要区分。当前读取探测没有擦写或编程命令；独立PRAM尝试也没有直接执行原厂Flash擦写路径，但未由此建立芯片存储状态在所有模式下都相同的保证。

下一步先在现有boot重复--probe，使用新输出目录，不再次刷诊断版。若CRC、差异数和前32字节稳定一致，可进一步与正常prebuilt完成初始化后的基线比较；若变化，先查读取模式/数据稳定性。不直接因为一次模型匹配就启用C7或自动编程。

本轮只做日志与离线模型分析，没有修改内核、编译、刷新boot或写触摸固件。
